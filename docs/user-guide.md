# User guide

LAMMPS-DPRc provides one source-built LAMMPS plugin for batched xTB QM/MM and
an optional compact DPA4c DPRc correction. The intended production layout is
one MPI rank per independent LAMMPS partition, with all partitions on one
GPU-local shared-memory node. The MPI implementation must provide an MPI-3
shared-memory communicator. The DeePMD path uses host `MPI_Gatherv`/
`MPI_Scatterv` staging and does not require an MPI unified shared-data window;
the xTBloom and classical CUDA brokers retain their own shared-window
requirements.

The plugin contains both the xTB QM/MM styles and the DeePMD C API adapter.
Users load only `dprcplugin.so`; a separate DeePMD LAMMPS plugin is neither
required nor supported by this workflow.

No production DPA4c model is distributed here. A loadable model is not
automatically an xTB DPRc model. Scientific use requires the qualification
program in [the DPA4c model plan](dpa4c-model-plan.md).

## Runtime components

Build all components with compatible compilers, MPI, LAMMPS integer sizes, and
CUDA runtime libraries:

- the pinned LAMMPS source and a Kokkos/CUDA-enabled `lmp` executable;
- the pinned xTBloom source and an explicitly selected shared library;
- DeePMD-kit with public C API version 30 or newer. API v30 provides
  `DP_DeepPotComputeCanonicalGraphGPU` for the validated packed
  block-diagonal fallback; API v31 or newer additionally provides the explicit
  `DP_DeepPotComputeCanonicalGraphBatchGPU` entry point;
- `libdeepmd_c.so` from that DeePMD build;
- a path-free artifact JSON generated by `tools/deepmd_artifact_manifest.py`
  that binds the declared clean source state, installed C header, and shared
  library by content;
- one compact canonical DPA4c model for `qmmm-dpa4c`;
- `dprcplugin.so` built against those exact headers and libraries.

The reviewed DeePMD reference pin in `config/dependencies.json` provides the
v30 canonical-graph entry point but predates the v31 explicit frame-axis
extension. The DeePMD-enabled build must use an explicit
`DPRC_EXPECTED_DEEPMD_REVISION`; do not present measurements from a dirty or
unpublished DeePMD checkout as release evidence.

Follow [Build and run LAMMPS](lammps-build-and-run.md) for the complete source,
LAMMPS, xTBloom, DeePMD C API, plugin, environment, and launch commands.

## Verify the installed runtime

Hash every runtime artifact and inspect the plugin dependencies:

```bash
sha256sum /path/to/lmp \
  /path/to/dprcplugin.so \
  /path/to/libxtbloom.so \
  /path/to/libdeepmd_c.so \
  /path/to/dpa4c-model.pt2

ldd /path/to/dprcplugin.so
readelf -d /path/to/dprcplugin.so
```

A DeePMD-enabled plugin must depend on `libdeepmd_c` and must not depend on a
standalone DeePMD LAMMPS plugin or expose DeePMD C++ implementation symbols.
The plugin binary is specific to the exact LAMMPS, MPI, compiler ABI, and
integer-size configuration used to build it.

Production workflow and benchmark records include the resolved `libdeepmd_c`
path, SONAME, and SHA-256. This loader identity is checked again before a saved
workflow invocation is reused. CMake separately rejects a DeePMD header or
library that does not match its declared source/header/library artifact cohort.
This declaration is not build attestation: it does not prove that the library
was compiled from the named checkout.

## Smoke-test xTB QM/MM

Run one window first:

```bash
python3 tools/etpeth_workload.py run \
  --tutorial /path/to/dprc-tutorial \
  --output /path/to/runs/etpeth-qmmm \
  --lammps /path/to/lmp \
  --plugin /path/to/dprcplugin.so \
  --xtbloom-library /path/to/libxtbloom.so \
  --library-dir /path/to/cuda/lib64 \
  --mode qmmm \
  --lammps-execution-backend host \
  --stage smoke
```

Then exercise synchronized batching:

```bash
python3 tools/etpeth_workload.py run \
  --tutorial /path/to/dprc-tutorial \
  --output /path/to/runs/etpeth-qmmm \
  --lammps /path/to/lmp \
  --plugin /path/to/dprcplugin.so \
  --xtbloom-library /path/to/libxtbloom.so \
  --library-dir /path/to/cuda/lib64 \
  --mode qmmm \
  --lammps-execution-backend host \
  --stage batch-smoke \
  --smoke-window-count 2 \
  --smoke-steps 25
```

One-window and batched results must pass the declared energy, force, charge,
SCC, and stable-slot checks before performance timing is eligible.

## Smoke-test QM/MM plus DPA4c DPRc

For a scientifically qualified model:

```bash
python3 tools/etpeth_workload.py run \
  --tutorial /path/to/dprc-tutorial \
  --output /path/to/runs/etpeth-dpa4c \
  --lammps /path/to/lmp \
  --plugin /path/to/dprcplugin.so \
  --xtbloom-library /path/to/libxtbloom.so \
  --deepmd-model /path/to/qualified-dpa4c.pt2 \
  --mode qmmm-dpa4c \
  --lammps-execution-backend host \
  --dpa4c-models-qualified \
  --library-dir /path/to/deepmd/lib \
  --library-dir /path/to/cuda/lib64 \
  --stage batch-smoke \
  --smoke-window-count 2 \
  --smoke-steps 25
```

The recommended host execution backend renders ordinary LAMMPS styles without
the `/kk` suffix and deliberately omits `-k on`. This prevents every umbrella
partition from creating an otherwise unused Kokkos CUDA context. The xTBloom
and DeePMD brokers remain GPU-backed; broker rank zero owns the DPA4c model and
performs one block-diagonal C API call across all synchronized partitions.
`--lammps-execution-backend kokkos` remains available only for separately
qualified Kokkos runs.

An unqualified model may be admitted only for private software diagnostics:

```text
--allow-unqualified-source --allow-unqualified-dpa4c-models
```

Every such record remains evidence-ineligible. The current in-plugin path
supports exactly one primary model and requires
`--model-deviation-frequency 0`. Ensemble model deviation is intentionally
rejected until it is implemented and independently qualified through the same
C API boundary.

## Run the resumable umbrella protocol

After both smoke tests pass, keep the runtime arguments immutable and run:

```bash
<same command> --stage anchor
<same command> --stage seeds
<same command> --stage equilibrate
<same command> --stage production
```

Long stages are split into hash-chained chunks. Resume is accepted only when
the executable, plugin, xTBloom library, model, generated input, start states,
manifest, environment, and prior outputs still match. Use
`--recover-stale-lock` only after confirming that the recorded process is dead.

## Direct LAMMPS use

The workflow runner is preferred because it records provenance and validates
resume state. For manual inputs, load only this plugin:

```lammps
plugin load /path/to/dprcplugin.so
```

The complete QM/MM plus DPA4c pair, KSpace, and fix commands are documented in
[Build and run LAMMPS](lammps-build-and-run.md#essential-qmmm-plus-dpa4c-lammps-commands).

## Precision and scientific acceptance

LAMMPS and xTBloom exchange IEEE binary64 values in atomic units at the public
xTBloom C ABI. The DeePMD canonical graph stores edge vectors in FP32 while
the C API publishes atomic energies, forces, and virials in FP64. This is an
explicit model/runtime capability, not permission to weaken scientific gates.

Any new FP32 or mixed-precision mode requires independent energy, force,
charge, SCC, trajectory, and free-energy qualification against the FP64
reference. Never loosen tolerances or regenerate references to admit a faster
result.

## Distribution limitations

The GPL-2.0-only LAMMPS and GPL-3.0-or-later xTBloom binary distribution
boundary remains unresolved. Do not distribute a combined plugin binary until
the owner records a licensing decision. DeePMD libraries and model artifacts
also require independent license, provenance, and redistribution review.
